## Задача 1 — мінімум у масиві

Шукаємо мінімальний елемент серед тих, що >= 2 * a[0][0]. Розмір масиву і діапазон задає юзер, значення рандомні.

Work Stealing — через ForkJoinPool, масив рекурсивно ріжеться навпіл поки блок не стане меншим THRESHOLD, далі fork/join. У ForkJoinPool кожен потік має свою чергу і як звільниться раніше за інших — краде задачі з чужої черги.

Work Dealing — звичайний fixed ThreadPool, рядки масиву наперед рівними шматками розкидані по потоках (скільки ядер — стільки шматків), далі кожен робить своє і все, ніхто нікому не допомагає.

**Різниця по часу:** запускав на масиві 5000x5000 (25 млн елементів) кілька разів підряд:

| | Work Stealing | Work Dealing |
|---|---|---|
| Прогін 1 | 41 мс | 38 мс |
| Прогін 2 | 36 мс | 40 мс |
| Прогін 3 | 39 мс | 37 мс |

Різниця в межах похибки, по факту майже однакова. Це логічно — тут кожен елемент масиву обробляється за однаковий час, тому навіть простий рівний поділ (dealing) вже дає збалансоване навантаження, красти особливо нема чого. Work Stealing почав би вигравати якби робота була нерівномірна (наприклад якщо частина рядків умовно "важча" за інші), а тут усі рядки однакові по складності обчислень.

Dealing навіть трохи легше пишеться, бо не треба думати про поріг дроблення і рекурсію — просто ділиш на N частин і все.

## Задача 2 — підрахунок символів у файлах

Рекурсивно обходить директорію, шукає текстові файли (txt, md, java, json, xml, csv, log і т.д.), рахує символи, виводить ім'я + кількість.

**Чому Work Stealing, а не Work Dealing:** файлова система це дерево, і наперед невідомо скільки файлів/папок і де. Одна папка може мати 2 файли, інша — 5000. Якщо ділити наперед (dealing) — половина потоків простоюватиме поки один розгрібає величезну папку. Fork/Join сам розкидає задачі по чергах і як тільки потік звільнився — хапає роботу з черги того хто застряг. Тобто обрав не тому що простіше (обидва варіанти пишуться приблизно однаково), а тому що для нерівномірного дерева директорій стілінг реально швидший і краще вантажить усі ядра.
